_Same pool. Labels on the bottles._

## The pool hasn't changed

**JavaScript is the pool.** Data and functions swim in the same medium.

TypeScript does not drain that pool or replace it.

It puts **labels on the bottles** so you can refuse the wrong drink *before* you sip.

<div data-marpit-fragment>

**TypeScript does not change how JavaScript runs.** It describes the shape of values so the compiler can reject illegal combinations before they ship.

</div>

---

## What TypeScript is

- A **superset of JavaScript** — every valid JS program is valid TS
- Adds **static types** that exist only at compile time
- Developed by **Microsoft**
- **Transpiles** to plain JavaScript (Next / Vite / `tsc` strip the types)

You will use it for the rest of this course: **Next.js**, then **React Native**.

---

## Why we bother

- **Contracts** between functions, components, and API responses
- **IDE support**: autocomplete, rename, jump-to-definition, squiggles
- **Shared types** across frontend and backend in a Next app
- **Refactoring** with a compiler as a safety net

It will not stop logic bugs. It will stop `user.name` on `undefined`, the wrong argument order, and props that a component never declared.

---

## Overview

1. **Types are erased** — the runtime is still JavaScript
2. **Structural typing** — compatibility by shape, not by name (unlike C#)
3. **Describing values** — objects, unions, discriminated unions
4. **Functions** — parameters, returns, `Promise<T>`
5. **Letting the compiler work** — inference, `unknown`, narrowing
6. **Reuse** — generics, a few utility types
7. **Next week** — component props, `strict`, fetch results

## Same function, three views

```javascript
function greet(name) {
  return `Hello, ${name}`;
}
greet(42); // "Hello, 42" — JS is happy, you may not be
```

```typescript
function greet(name: string): string {
  return `Hello, ${name}`;
}
greet(42); // compile error: number is not assignable to string
```

```javascript
// What actually runs in the browser — types gone
function greet(name) {
  return `Hello, ${name}`;
}
```

If it is not in the emitted JavaScript, **`typeof`, `instanceof`, and the network cannot see it.**

---

## Erasure in practice

- `interface`, `type`, and generics **do not exist at runtime**
- `typeof` still reports JavaScript's runtime types (`"string"`, `"object"`, …)
- Next (and your editor) type-check; the browser only receives JS

[TypeScript Playground](https://www.typescriptlang.org/play) — paste examples from this lecture and hover the types.

# Structural vs nominal typing

---

<!-- class: lead -->

## Names vs shapes

C# (and Java) mostly use **nominal typing**: two types are compatible when they share an explicit declared relationship (`implements`, `extends`). The name and the hierarchy matter.

TypeScript uses **structural typing**: two types are compatible when they have the **required shape**. If it has `name` and `quack()`, it can be used as a `Duck`.

This is the duck (typing) test, enforced by the compiler.

---

## Three differences that matter

| | Nominal (C#, Java) | Structural (TypeScript) |
| --- | --- | --- |
| **Compatibility** | Declared identity / hierarchy | Shape of the data |
| **Same members, different types** | Not interchangeable | Interchangeable |
| **Tradeoff** | Safer when names carry meaning; slower to compose | Fast to compose and pass data; can mix values that merely look alike |

## C#: the name is what counts

```csharp
public interface IDuck {
    string Name { get; set; }
    void Quack();
}

public class Mallard : IDuck {
    public string Name { get; set; }
    public void Quack() => Console.WriteLine($"{Name} quacks!");
}

public class Person {
    public string Name { get; set; }
    public void Quack() => Console.WriteLine($"{Name} tries to quack...");
}

void Speak(IDuck duck) => duck.Quack();

Speak(new Mallard { Name = "Donald" }); // OK
Speak(new Person { Name = "Bob" });     // Error: Person does not implement IDuck
```

## TypeScript: the shape is what counts

```typescript
interface Duck {
  name: string;
  quack(): void;
}

class Mallard {
  constructor(public name: string) {}
  quack() {
    console.log(`${this.name} quacks!`);
  }
}

class Person {
  constructor(public name: string) {}
  quack() {
    console.log(`${this.name} tries to quack...`);
  }
}

function speak(duck: Duck) {
  duck.quack();
}

speak(new Mallard("Donald")); // OK
speak(new Person("Bob"));     // OK: same shape
```

## The cost: same shape is not the same meaning

```typescript
type UserId = string;
type OrderId = string;

function refund(orderId: OrderId) {
  /* ... */
}

const userId: UserId = "alice-1";
refund(userId); // allowed — both are just string
```

Structural typing will not protect “this string means a user” vs “this string means an order.”

Watch for that when ids, units, and look-alike objects flow through an app.

## Extra fields: variables vs object literals

Passing a value that **already exists** may have extra properties. TypeScript only requires the properties the function asked for.

**Object literals** are checked more strictly (excess property checks). Typos and leftover fields are caught there.

```typescript
type Bottle = { label: string; ounces: number };

const pantry = { label: "DRINK ME", ounces: 4, extra: true };
const fromPantry: Bottle = pantry; // OK — extra is ignored, not an error

const sip: Bottle = {
  label: "DRINK ME",
  ounces: 4,
  extra: true, // Error: "extra" is not on Bottle
};
```

## Why this is well suited to components

A React component declares **the shape of its props**. Anything with that shape can be passed in. You do not need a class hierarchy of `IButtonProps`.

```typescript
type ButtonProps = {
  label: string;
  onClick: () => void;
};

function Button({ label, onClick }: ButtonProps) {
  onClick();
  return label;
}

Button({ label: "Eat me", onClick: () => console.log("clicked") });
```

Props are just an object. You will write this same pattern in JSX shortly.

## Postfix types (you already know the values)

Types come **after** the name.

```typescript
let isOpen: boolean = false;
let age: number = 25;
let guest: string = "Alice";
let seats: number[] = [1, 2, 3];
```

You rarely need to write these. If the right-hand side is obvious, **let the compiler infer**.

Prefer `string[]` for lists. Tuples (`[string, number]`) exist for fixed-length pairs; you will see them more in library types than in your own code.

## Object shapes

```typescript
type Guest = {
  name: string;
  age: number;
  hat?: string; // optional
  readonly id: number; // cannot be reassigned
};

const alice: Guest = { name: "Alice", age: 7, id: 1 };
alice.id = 2; // Error
```

- `?` — may be missing (`undefined`)
- `readonly` — the property cannot be reassigned on that object
- Nested objects are typed the same way: more shapes inside shapes

## `type` vs `interface`

Both can describe object shapes. **Do not spend energy picking a favorite.**

| Use | Why |
| --- | --- |
| `type` | Unions, intersections, and aliases of primitives (`type Id = string \| number`) |
| `interface` | Object shapes that you may want to `extend`, or that a library merges |

```typescript
type Id = string | number;

interface Guest {
  name: string;
}

interface SeatedGuest extends Guest {
  chair: number;
}
```

In this course, `type` for most things is a perfectly good default.

## Union types

A value that can be **one of several** things: `|`.

```typescript
type PartyStatus = "waiting" | "seated" | "over";
type Id = string | number;

let status: PartyStatus = "waiting";
status = "fashionably late"; // Error

function findGuest(id: Id) {
  return String(id);
}
```

## Discriminated unions — UI state

Give each variant a **shared tag** (`status`, `kind`, `type`). After you check the tag, TypeScript knows the rest of the fields.

```typescript
type LoadState =
  | { status: "idle" }
  | { status: "loading" }
  | { status: "success"; data: string }
  | { status: "error"; message: string };

function render(state: LoadState): string {
  switch (state.status) {
    case "idle":
      return "Click to load";
    case "loading":
      return "…";
    case "success":
      return state.data;
    case "error":
      return state.message;
  }
}
```

This is the usual way to type “a screen that is loading, failed, or showing data.”

## Parameters, returns, and function types

```typescript
function greet(name: string): string {
  return `Hello, ${name}!`;
}

const multiply = (a: number, b: number): number => a * b;

type MathFn = (x: number, y: number) => number;
const add: MathFn = (a, b) => a + b;
```

- Annotate **parameters** (the compiler often infers the return)
- A **function type** is a reusable signature — the same idea as typing a callback or an `onClick`

## Optional, default, rest

```typescript
function greet(name: string, age?: number, greeting = "Hello") {
  console.log(`${greeting}, ${name}, age ${age ?? "unknown"}`);
}

function sum(...numbers: number[]): number {
  return numbers.reduce((total, n) => total + n, 0);
}

greet("Alice");
greet("Bob", 25);
greet("Hatter", 30, "Tea?");
sum(1, 2, 3, 4);
```

Optional parameters (`?`) must come **after** required ones. Defaults make the parameter optional automatically.

## Async functions return promises

An `async` function always returns a `Promise`. `await` unwraps `Promise<T>` into `T`.

```typescript
type CanEnter = (age: number, event: string) => Promise<boolean>;

const canEnter: CanEnter = async (age, event) => {
  return event === "tea party" && age >= 7;
};

const ok = await canEnter(7, "tea party"); // boolean
```

If you type a return as `string` on an `async` function, that is a mistake — it is `Promise<string>`.

This is last session’s async/await, with labels on the values that arrive later.

## Inference

If TypeScript can see the value, you do not need to repeat the type.

```typescript
let message = "Hello TypeScript"; // string
let numbers = [1, 2, 3]; // number[]
let mixed = [1, "hello", true]; // (number | string | boolean)[]

const names = ["Alice", "Hatter", "Rabbit"];
names.forEach((name) => console.log(name.toUpperCase())); // name is string
```

Annotate **boundaries**: function parameters, public component props, data from JSON / `fetch`.

Leave **interiors** inferred: locals, obvious returns, callbacks.

## `any` vs `unknown`

`any` turns the checker off for that value. You can call anything, access anything, pass it anywhere. **Avoid it** — it punches a hole in the rest of the file.

`unknown` means “I do not know yet.” You **must narrow** before using it.

```typescript
function handle(value: unknown) {
  value.toUpperCase(); // Error

  if (typeof value === "string") {
    value.toUpperCase(); // OK
  }
}
```

`JSON.parse`, many library callbacks, and `error` in `catch` are closer to `unknown` than to a typed object. Treat them that way.

## Narrowing and type guards

A **narrowing** check is a runtime test the compiler understands. After it, the type is smaller.

```typescript
function processValue(value: string | number) {
  if (typeof value === "string") {
    console.log(value.toUpperCase());
  } else {
    console.log(value.toFixed(2));
  }
}

function isGuest(value: unknown): value is { name: string } {
  return (
    typeof value === "object" &&
    value !== null &&
    "name" in value &&
    typeof value.name === "string"
  );
}

function greet(raw: unknown) {
  if (isGuest(raw)) {
    console.log("Welcome, " + raw.name); // raw is { name: string }
  }
}
```

`typeof`, `===` on a discriminant, `in`, and `Array.isArray` are the usual tools. A custom guard uses `value is Type` as the return type. After a true check, the argument is that type.

## Generics: “this works for some type T”

A generic is a **type parameter**. You use it when the relationship between inputs and outputs is the same for many types.

```typescript
function first<T>(items: T[]): T | undefined {
  return items[0];
}

first(["Alice", "Hatter"]); // T inferred as string
first([1, 2, 3]); // T inferred as number
```

You will meet this immediately in React:

```typescript
const [guest, setGuest] = useState<string | null>(null);
```

`Array<T>`, `Promise<T>`, and `useState<T>` are the same idea: a box that keeps its contents typed.

## Utility types you will actually use

Built-in transformers of existing types. Reach for these before writing a near-copy of a type.

```typescript
type Guest = {
  id: number;
  name: string;
  email: string;
  age: number;
};

type GuestDraft = Partial<Guest>; // all optional — a form in progress
type GuestName = Pick<Guest, "name" | "email">; // a list row
type GuestPublic = Omit<Guest, "id">; // what the client may send
```

- `Partial<T>` — every property optional
- `Pick<T, K>` — keep only these keys
- `Omit<T, K>` — everything except these keys

## Typing component props

Same as the `Button` shape earlier; this is what you will write in React.

```tsx
type CardProps = {
  title: string;
  count?: number;
};

export function Card({ title, count = 0 }: CardProps) {
  return (
    <article>
      <h2>{title}</h2>
      <p>{count}</p>

// <Card title="Tea party" />
// <Card title="Tea party" count={3} />
```

Destructure props, type the object, give defaults in the parameter list.

## Data from the network is `unknown`

`fetch` + `.json()` is not a typed API. The compiler cannot see the HTTP body.

```typescript
type Guest = { name: string; id: number };

async function loadGuest(url: string): Promise<Guest> {
  const response = await fetch(url);
  const data: unknown = await response.json();

  if (!isGuest(data)) {
    throw new Error("Unexpected guest payload");
  }
  return data; // isGuest is the type guard from the previous section
}
```

Do not write `const data: Guest = await response.json()` and hope. Narrow, or use a validator (you will see libraries for this later). Until then, `unknown` + a type guard is best.

## Summary

The pool is still JavaScript. TypeScript **labels the bottles** and is **erased** before runtime.

- **Structural typing**: compatibility by shape. Fast for props; watch look-alike types.
- **Describe values** with objects, unions, and **discriminated unions** for UI state.
- **Annotate boundaries**; infer the rest. Prefer `unknown` over `any`.
- **Narrow** with runtime checks. Generics and `Partial` / `Pick` / `Omit` keep types DRY.
- **Next week**: type props, live in `strict`, treat JSON as `unknown`.
